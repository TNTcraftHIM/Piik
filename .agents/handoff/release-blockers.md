## 1. P0, security: The App's OriginReader fetches any http(s) URL named in a shared webpage's HLS or DASH manifest, including loopback and private-network hosts, from the sharer's machine, and serves the response bodies to room peers.

- Where: `prototype/channel-server/src/app_page/reader.rs:676` (surface: external; READ)
- Scenario: Room member M hosts a webpage with an HLS manifest whose segment URIs are http://127.0.0.1:39721/api/client-launcher or LAN services such as a router, NAS or local dev server. M asks victim V to watch it together. V opens the page in the Piik App and picks 'Share this video' or 'Forward'. V's App admits every manifest URI as a readable resource. When M's client reads those resource IDs over the watch byte route, V's App makes the GET from V's machine and returns the bodies to M. A browser would refuse this through CORS and Private Network Access. The App's own launcher API answers a request with no Origin, so M learns V's approved sites, LAN addresses, tunnel publicOrigin and localSite.
- Chain: ChannelShareControl.tsx:524-529 -> session.ts:2713-2719 selectWatchForwardSource (or session.ts:2800-2829 setWatchByteSource) -> app_page.rs:464-473 OriginReader::prepare -> app_page.rs:510 RegisterWatchReader -> reader.rs:455 playlist -> reader.rs:676-706 admit. admit accepts any URL that passes app_page.rs:240-248 valid_url, which checks only scheme, host and userinfo. mpd_native.rs:73-82 skips valid_url entirely. A peer read goes reader.rs:239-306 window -> reader.rs:156-238 response (reqwest GET, with page cookies when same-origin) -> body returned at reader.rs:328-393, with no Content-Type check. The App loopback access middleware lets a GET to /api/client-launcher with no Origin through, checking only Host (app.rs:694-700, 721-741). The response content is at app.rs:845-877 and app_domain.rs:129-156. Checks I looked for and did not find: no is_private, is_loopback or is_link_local destination filter in channel-server/src outside app.rs:460, app_tunnel.rs and web.rs. No check after DNS resolution. No restriction of children to the root's origin. I did not trace the peer-side authorization of watch byte reads in channel-native; I took it from the doc comment at reader.rs:1.
- Reproduction: 1. M serves https://m.example/page.html. The page plays https://m.example/a.m3u8 through hls.js or a native <video>, served as application/vnd.apple.mpegurl. The manifest is: #EXTM3U #EXT-X-TARGETDURATION:6 #EXTINF:6, http://127.0.0.1:39721/api/client-launcher #EXTINF:6, http://192.168.1.1/ #EXT-X-ENDLIST 2. V, in the same room, opens the page in the Piik App page player and picks Share this video (the Direct HLS choice). 3. app_page.rs:464-473 runs OriginReader::prepare. prove_root reads the root, and rewrite admits both URIs as File children whose UUIDs appear in the rewritten manifest. 4. M's client (or a modified one) reads the root and gets the child UUIDs. It then issues watch byte reads for the first UUID at offset 0, length 65536. 5. V's App sends GET http://127.0.0.1:39721/api/client-launcher with Range and no Origin. The middleware lets it through, the server answers 200 with Content-Length and the launcher JSON, and reader.rs:350-431 returns those bytes to M. M now has V's approved sites, publicOrigin, localSite and LAN addresses. The second UUID does the same for the router page. Proof test: a reader.rs unit test that serves a public manifest whose segment URI points to a second loopback axum listener. Call OriginReader::prepare, read the child UUID from the snapshot, call reader.read(child, 0, 65536) and assert the second listener's body comes back. This passes today. Fix direction: give the App's origin fetch one destination policy that refuses loopback, link-local and private addresses after DNS resolution (and on redirects), or pins children to the root's origin. It belongs in the reqwest client or a custom resolver, not in each caller.

## 2. P0, bounded-resource: Every anonymous Join creates a permanent, persisted user, and nothing caps the number of users or ever prunes them

- Where: `prototype/channel-core/src/identity.rs:279` (surface: admission; READ)
- Scenario: Anyone who can reach /prototype/channel (the site link; the Origin check is forgeable by a non-browser client) runs a loop: open a WebSocket, send join with no credential, optionally set_profile with a 24 KiB avatar, send leave. Each pass adds one user to the in-memory BTreeMap and one row to channel.sqlite. Leave removes only the session, so the 128-session cap never applies. Memory and disk grow without limit, about 24 KiB per pass, and each pass is also an fsync'd SQLite write inside the Hub mutex. Startup loads every row back into memory. Profile search is O(N) under the Hub lock, so it stalls the whole site as the table grows.
- Chain: domain.rs:478-514 session() -> Hub::request -> domain.rs:77 changes_metadata -> lib.rs:201-202 -> identity.rs:243-252 admission_changes_user(None,None)=true -> lib.rs:308-312 handle -> lib.rs:627-674 join -> channel.rs:206-216 -> identity.rs:279 Uuid::new_v4 + identity.rs:306-312 users.or_insert_with -> domain.rs:119-121 save_user -> storage/domain.rs:64-75 INSERT domain_user. Leave: lib.rs:537 -> channel.rs:389-393 -> channel.rs:434 removes the session only. No users.remove or retain anywhere (grep). Avatar limit wire.rs:343 (24 KiB). Reload: storage/domain.rs:55-60. Amplifiers: identity.rs:159-196 (O(N) NFC search), identity.rs:342-351 (linear credential scan on every join and bearer request). Looked for a user cap, rate limit, per-address limit or pruning and found none. Retaining identities is deliberate (channel-storage-and-identity.md:32-35), but their number has no bound.
- Reproduction: Shortest path, using any WebSocket client against a hosted site: loop { connect ws(s)://<site>/prototype/channel with header Origin: <site origin>; send {"type":"join","protocol":<CHANNEL_PROTOCOL>,"name":"x",...} with no credential or owner_key; wait for Welcome; optionally send set_profile with an avatar up to 24 KiB; send leave (or just close) }. After N passes, identity.users.len() and SELECT COUNT(*) FROM domain_user have each grown by N. The live session count stays near 0, so channel_full never fires. Restarting the server loads all N rows back into memory. A probe that proves it without the network is a channel-core unit test: build an Authority, then for i in 0..10_000 call handle(Uuid::new_v4(), Join{no credential}, now) followed by handle(same connection, Leave, now). Assert that channel.identity.users.len() == 10_001 (including any owner entry) and that channel.identity.sessions is empty. On the server side, the same loop through Domain::request with a temp SQLite file shows the domain_user row count growing by one per join.

## 3. P0, bounded-resource: Room grants have no size bound: one reusable invite key or password admits unlimited fresh identities, rewrites the whole policy on each entry, and inflates the manager's members list toward the 4 MiB frame limit

- Where: `prototype/channel-core/src/access.rs:227` (surface: admission; READ)
- Scenario: Someone holds a private room's invite link. The key is reusable, never expires and still works after that person's access is removed. They repeat F1's loop and add enter_room {inviteKey} for each fresh identity. Every entry inserts a new grant, and the room writer rewrites the full policy (O(N) per entry). The manager's view carries every grant as members, and the domain does not check its length. At roughly 100k grants (39 bytes per UUID in JSON) the host's HostOutput no longer fits the 4 MiB inbound frame. The host's socket is then closed on every attempt, and because the grants are durable policy, re-registration resends the same oversized projection. The manager's own state events also exceed the browser's 4 MiB event limit. The room can no longer be hosted or managed.
- Chain: lib.rs:529-531 command_room -> channel.rs:776, 1225-1296 forward_room -> host.rs:771-778 (policy_changed) -> room.rs:746-753 -> access.rs:209-228 grants.insert with no size check (grep: no grants.len bound) -> host.rs:1937-1938 clones the whole policy for the write. Members: access.rs:275 -> room.rs:302 -> host.rs:564. accept_host checks only members.is_some() && !can_manage (channel.rs:1611). Frame caps: domain.rs:235-236 / wire.rs:8 (4 MiB), session.ts:487-488 / protocol.ts:226. The frame-limit outcome is inferred from code. Overhead was not measured, and the Native client's outbound limit was not read.
- Reproduction: An attacker holds the invite link (room id plus key) to a private room. In a loop: open the domain WebSocket, send Join{name:"x", credential:null}, which mints a new user (identity.rs:276-282). Then send EnterRoom{roomId, inviteKey}, which grants the user (access.rs:227) and rewrites the whole policy on disk (stored_room.rs:200-203). Then send Leave, which frees the session slot (channel.rs:389). Repeat about 100k times. Nothing rate-limits or rejects the loop. Each UUID costs about 39 bytes of JSON in members, so the manager's room view passes 4 MiB. From then on the manager's browser rejects Welcome/State ("Channel event exceeds frame limit", session.ts:488). If the room has a remote Native or browser host, that host's HostOutput breaks the domain socket's 4 MiB max_message_size (domain.rs:235) whenever a manager session is present. Test that would prove it: a core unit test in the style of discovery.rs:1560. Build a RoomRuntime with a Private RoomState, call policy.enter(Uuid::new_v4(), None, Some(&key)) 110_000 times, then serialize Command::HostOutput for a projection with the creator's endpoint present, and assert that its length exceeds CHANNEL_MESSAGE_BYTES. Nothing in enter, validate, accept_host or within_domain_frame rejects or trims it.

## 4. P0, authorization: The App's loopback control API trusts any local principal that forges Host/Origin headers, so another Android app (or another OS account on a desktop) can get the hosted site's owner ticket, approve its own website, and drive the App as any approved site

It gets back the site URL with a fresh &launch=<ticket>, then joins the site's local WebSocket with ownerKey=<ticket>. The domain swaps the ticket for the owner admission key, so the app is now owner of the user's site and can read and delete rooms and export backups. Checked and not found: any secret on launcher routes; any use of SO_PEERCRED or a pipe DACL like owner_link.rs:84-112/155-184; any Android-side binder/permission gate in front of the socket (the manifest exposes nothing else; the Rust server is the only gate).

## 6. P0, bounded-resource: Room exports that are never read each hold a blocking-pool thread and a full temporary copy of the room database until the connection drops, and nothing limits how many can be open at once.

- Where: `prototype/channel-server/src/backup.rs:76` (surface: backup-storage; READ)
- Scenario: A member who created a room on a Hosted-mode Server grows its archive past the socket buffers: a few MB, e.g. about 20 inline images or one room-copy upload. They then send GET /prototype/channel/rooms/{room}/backup over and over, with their bearer token, and never read the responses. Each request copies the room DB into a temp directory, then spawn_blocking writes the zip into a 64 KiB duplex through SyncIoBridge, which blocks that thread once the client stops reading. The thread and the temp DB stay held for the life of the connection. At tokio's default 512 blocking threads, every room turn on the Server waits behind them, because each room input runs on spawn_blocking. Chat, join and share then stop in every room. Before that point, the temp copies can fill the disk.
- Chain: domain.rs:833-834 -> domain_backup.rs:89-96 export (Hosted creators allowed, 82-85) -> backup.rs:42-61 HostCommand::Snapshot -> session.rs:2849-2930 (snapshot_job serializes only the copy step, 2853-2860; temp DB via storage.rs:222-268) -> backup.rs:62-69 closure keeps `snapshot` alive -> backup.rs:72-88 archive(): tokio::io::duplex(64*1024) + spawn_blocking(write) blocks in SyncIoBridge. Shared pool use: session/room_owner.rs:163 runs every room input on spawn_blocking. Not found: a limit on concurrent exports, a write or idle timeout on the HTTP server (web.rs:27-45, axum_server defaults), or a byte budget for snapshot temp copies.
- Reproduction: 1. Start a Hosted-mode Server, either standalone or on the LAN HTTPS entry. As a member allowed to create rooms, create a room and grow its archive to about 8 MB or more, for example by posting inline images. 2. In a loop, open a new TCP connection with a small SO_RCVBUF and send `GET /prototype/channel/rooms/{room}/backup` with `Authorization: Bearer <own token>`. Never read the response, and retry when the answer is 409 room_busy. Each accepted request leaves one spawn_blocking writer stuck in SyncIoBridge (backup.rs:78) and one piik-backup-* temp DB on disk (session.rs:2910). 3. After about 512 connections, a chat message in any other room gets no response: its room input is queued at room_owner.rs:163. Behind the documented nginx (60 s send_timeout), keep re-issuing about 9 exports a second to the same effect. A test that would prove it: in channel-server, build the runtime with `tokio::runtime::Builder::new_multi_thread().max_blocking_threads(2)` and set up a Hosted domain with a room larger than the buffers. Issue 2 exports through the router and hold their response bodies without polling them. Then assert that a room command, such as a chat post through the room-owner path, does not finish within a timeout. The fix to check against: put a permit on export, as restore already has with room_restore, or a timeout on the writer.

## 9. P0, bounded-resource: The Server and App HTTP entries have no header-read timeout, idle timeout or connection cap, so one peer can hold unbounded sockets and up to about 400 KiB of buffered headers per socket

- Where: `prototype/channel-server/src/web.rs:33` (surface: server-http; READ)

- Chain: web.rs:27-45 serve_http -> axum_server::from_tcp(...).serve(...) never sets a hyper Timer (axum-server 0.8.0 source has no `timer`); hyper 1.12 server/conn/http1.rs:253 sets header_read_timeout to 30 s by default, but per http1.rs:364 it needs a Timer to take effect, so it does nothing here. The axum-server accept loop (server.rs:286-338) spawns one task per socket with no limit, and on an accept error it sleeps and retries (server.rs:370-377). HTTPS: domain.rs:848-854 uses the rustls acceptor, whose timeout covers the handshake only (tls_rustls/mod.rs:126). App LAN bind: app_domain.rs:265-266, 479-495 -> web.rs:82-96. The existing test web.rs:652-692 shows incomplete headers survive until shutdown. The documented nginx front (README.md:229-234) bounds this only for the proxied Server deployment.
- Reproduction: 1. Start the App in Local mode and select a LAN address. app_domain.rs:265 then binds the HTTPS entry on <lan-ip>:<port>. 2. From another host on the same LAN, open N TCP connections to <lan-ip>:<port>, finish the TLS handshake on each (for example with `openssl s_client` in a loop, or a small rustls client), then send nothing. Alternatively send "GET / HTTP/1.1\r\nX: " and then one byte every few seconds, so each socket's buffer grows toward about 408 KiB. 3.
