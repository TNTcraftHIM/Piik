# 屏幕共享项目需求理解

## 2026-08-18 13:31

## 需求概述

构建一个面向熟人游戏场景的低延迟屏幕共享工具。分享者可以在私密房间内分享游戏、应用窗口或显示器画面及声音，多名朋友可以即时观看。系统采用类似 Photon Host Mode 的产品抽象：中心服务负责房间、身份和建立连接，媒体默认通过 WebRTC 在客户端间 P2P 传输；STUN 协助打洞，直连失败的单条链路才使用 TURN。分享端 Web 优先并允许后续 Electron/原生增强；观看端必须可通过桌面或手机浏览器打开邀请链接，不绑定专用客户端。

当前 PoC 的硬上限为一名分享者和三名观看者，第四名观看者会被明确拒绝。只有在上行带宽和编码负载完成测量后，后续版本才重新评估是否放宽。产品不承担公开直播或大规模观看，相关需求交给 OBS/Twitch 等成熟直播服务。

## 功能需求

### P0 - 必须实现

- [ ] 私密房间：用户可创建房间，并通过不可猜测且可过期的链接或邀请码让朋友加入。
- [ ] 免安装观看：桌面和手机观看者可直接通过浏览器链接进入、授权并播放，不依赖与分享端相同的桌面客户端。
- [ ] 屏幕采集：分享者可主动选择显示器或应用窗口，开始、停止和切换分享状态。
- [ ] 游戏声音：Windows Chrome/Edge 目标环境可请求系统音频；没有返回音轨时必须明确提示，而不是静默无声。
- [ ] 一对多观看：一名分享者可同时向至少三名观看者发送画面，每名观看者拥有独立的 WebRTC 连接与状态。
- [ ] P2P 优先：ICE 必须先尝试直接 UDP 路径，服务器不得默认中转可直连的媒体。
- [ ] NAT 兜底：每名观看者独立进行 ICE；必须提供 TURN/UDP、TURN/TCP 与 TURN/TLS 443 candidates，通过优先级偏好直连和 UDP，同时允许严格网络选择 TCP/TLS，不能因为其网络与其他观看者不同而静默失败。
- [ ] 质量档位：至少提供 1080p60、720p60、720p30 三档目标，并根据拥塞主动降档。
- [ ] 断线恢复：临时网络变化时尝试 ICE restart 和重连，并向用户显示当前连接状态。
- [ ] 可观测性：采集候选类型、RTT、丢包、抖动、实际码率、帧率、编码耗时和质量受限原因。
- [ ] 访问控制：未获授权的用户不能观看、发布或获取长期 TURN 凭据。

### P1 - 重要功能

- [ ] 分享端桌面封装：用 Electron 固定 Chromium 版本、改善选源/热键/系统音频体验，同时保留 Web 观看端。
- [ ] Windows 应用音频：仅捕获所选游戏及其子进程的音频，避免把语音聊天或通知声一并分享。
- [ ] 连接自检：在开始分享前验证信令、STUN、TURN/UDP 和 TURN/TLS 可达性，并给出不暴露凭据的诊断结果。
- [ ] 运行时编解码选择：根据端点能力和统计数据选择实际硬件编码的 H.264、VP8、VP9 或 AV1，并始终保留兼容回退。
- [ ] 诊断页面：用户可导出不含敏感地址和凭据的连接诊断信息。

### P2 - 可选功能

- [ ] 原生 Windows 捕获辅助程序，使用 WGC/DDA、WASAPI 和硬件编码器降低复制与编码开销。
- [ ] 多地区 TURN 调度与按地区、运营商统计直连率。

## 非功能需求

- 性能：在 RTT 不高于 40 ms、丢包不高于 1% 的受控 P2P 路径中，玻璃到玻璃延迟目标为 p50 不高于 150 ms、p95 不高于 250 ms；区域 TURN/UDP 路径的 p95 目标不高于 350 ms。
- 启播：观看者请求观看后，除用户授权耗时外，3 秒内出现首帧。
- 流畅性：选择 60 fps 档位时，不能在没有降档或提示的情况下连续 5 秒低于 50 个解码帧每秒。
- 成本：直连媒体不经过服务器；STUN 与信令仅承担小流量；TURN 的实际流量必须可计量、限额和告警。
- 安全：全程 HTTPS/WSS，媒体使用 WebRTC DTLS-SRTP；TURN 使用短期凭据、配额和速率限制；仓库不得包含真实密钥。
- 隐私：P2P 会向房间内好友暴露网络地址，首版威胁模型仅覆盖可信熟人；若要求隐藏 IP，必须切换为服务器转发。
- 可维护性：代码、需求、调研、项目记忆、`AGENTS.md` 和 `.codex/` 均在 Git 中跟踪；开发配置不得依赖单一操作系统的绝对路径。
- 兼容性：分享端首个目标矩阵为 Windows 10/11 的当前 Chrome/Edge；观看端还必须覆盖当前 Android Chrome 和 iOS Safari，并实测自动播放限制、横竖屏、锁屏恢复与移动网络切换。

## 边界与约束

- 首版不包含远程键鼠控制、公开/大规模直播、录制、社区系统或完整语音聊天；大规模分享直接使用现有直播服务。
- 首版不以超过三名观看者为正常工作负载，也不承诺跨洲网络下的固定低延迟。
- 浏览器规范要求每次由用户主动选择分享源，权限不能永久保存；纯网页不能保证指定游戏窗口或始终获得系统音频。
- 1080p60 是能力目标，实际分辨率、帧率和硬件编码由浏览器、GPU、驱动、画面复杂度及网络共同决定。
- 首版不实现 SFU，不从零实现编解码器或自定义 UDP 视频协议；产品范围以后改变时重新立项，而不是预留复杂框架。
- GPL/AGPL 项目在许可证策略确认前仅用于研究，不能直接复制到计划闭源的产品中。

## 验收标准

### P2P 建立与 TURN 兜底

- Given 两端网络允许 UDP 打洞，When 观看者加入，Then `getStats()` 显示选中的候选对不是 `relay`，且服务器没有承载媒体流量。
- Given 模拟对称 NAT 或封锁直连，When 观看者加入，Then 系统自动选择 TURN 并在界面标识“中继连接”，无需用户配置端口。
- Given UDP 被封锁但 TLS 443 可达，When ICE 检查发现 direct 与 TURN/UDP candidates 不可用，Then 可用的 TURN/TLS candidate 能建立连接或返回可诊断的明确失败原因。
- Given 同一房间中一名观看者可以直连、另一名处于严格 NAT 或移动网络，When 两者同时观看，Then 前者保持 P2P，后者单独使用 TURN，双方都能看到同一分享且互不影响。

### 浏览器与移动端观看

- Given 观看者只有受支持的手机浏览器，When 打开有效邀请链接并执行浏览器要求的播放手势，Then 无需安装应用即可进入房间、看到首帧并听到可用音频。
- Given 手机从 Wi-Fi 切换到蜂窝网络或页面从后台恢复，When 原候选对失效，Then 客户端执行 ICE restart 或重建连接，并显示恢复进度而不是永久黑屏。

### 一对多与带宽保护

- Given 一名分享者和三名观看者，When 选择 1080p60，Then 三名观看者可独立加入和离开，任一观看者离开不会中断其他连接。
- Given 新观看者会使预计总上行超过安全预算，When 其请求加入，Then 系统自动降低档位、拒绝该档位或建议改用外部直播服务，而不是持续堆积发送队列。

### 质量和恢复

- Given 受控 RTT/丢包测试条件，When 连续分享高动态游戏画面 30 分钟，Then 延迟、帧率与丢帧达到上述目标，且没有不可恢复的冻结。
- Given 分享过程中切换 Wi-Fi/有线网络，When ICE 连接失败，Then 客户端触发 ICE restart，并在成功或超时后给出明确状态。
- Given 浏览器未返回系统音轨，When 分享开始，Then 分享者在启播前看到“当前来源没有可共享音频”的提示。

### 仓库可移植性

- Given 在新的 Windows、macOS 或 Linux 工作副本中克隆仓库，When 打开项目，Then 需求、调研、项目记忆、`AGENTS.md` 与 `.codex/` 均存在且处于 Git 跟踪状态，不依赖原开发机器的绝对路径或密钥。

## 待确认事项

- 后续版本是否应在测量通过后放宽三名观看者的硬上限。
- 首版是否必须只捕获所选游戏的声音，还是允许整机系统音频。
- 项目许可证及是否计划闭源商用。
- 首批用户主要位于香港、内地还是跨地区；该信息决定 TURN 部署位置和测试矩阵。
- iOS Safari 与 Android Chrome 的最低版本及是否要求平板适配。

详细技术证据、参考代码和难度评估见 `docs/research/webrtc-p2p-screen-sharing.md`。
